# Epic Board

Status: active

## The epic

Epic Board is for one person planning and building a project with Kiro. They open a Kiro Crew app and see the whole plan on one board: every spec as a card, in Planned, In progress and Done columns, with how many of its tasks are ticked. The board works on any Kiro project, because every spec in `.kiro/specs/` is a card whose column comes from its tasks. When the project also has epics, the cards are grouped under them, and stories that have no spec yet appear as planned cards. Specs that belong to no epic sit under "No epic". They click a card and start a Crew conductor on it: it writes the spec on a branch when there is none, or builds the next task group when there is one, and opens a pull request to review. It never merges. The conductor's chat opens beside the board, so they approve its tool calls, answer its questions and steer it without leaving the board.

It matters now because the plan already lives in files on main, and nothing shows it at a glance or turns "what's next?" into work started. The board reads only main and never edits it, so it always shows what has landed, and the plan changes through Kiro as before. A started story shows its chat's status (working, needs you, interrupted or idle) and opens its chat, a card moves to In progress when you start it and to Done when its work lands on main.

## Not in this epic

- Editing the plan from the board: moving cards, changing statuses or writing epic files.
- The board following a conductor's work for the person. The board shows one of six states for the story's chat and its workers and embeds Crew's own chat for the person to use. The board's own code does not read the chat's messages, and does not approve or answer anything for the conductor.
- Merging. The conductor opens pull requests and the person reviews and merges them.
- Creating or renaming the person's Crew folders, or editing their project directories. The board reads the person's folders; Crew manages them. Exception: when "Start each story in its own worktree" is on for a project, the board creates one Crew subfolder per started card to set that card's working directory. Crew refuses to delete folders for apps, so on Finish session the board clears the subfolder's project directory instead.

- [Set up projects](../../.kiro/specs/set-up-projects/) — done. A Projects view lets the person pick which Crew folders the board shows, without editing `config.json` by hand. Built after "Switch projects".
- [A worktree per card](../../.kiro/specs/a-worktree-per-card/) — done. Each started card gets its own worktree, made fresh from the latest main, and a Crew subfolder, so several conductors can work on one project at once. The person ends the session with the Finish session button on the card: the board removes the worktree only when nothing is uncommitted or unpushed, marks the card Session finished and posts a note in the chat. Restart session opens a new chat and a new worktree. There is no automatic cleanup. Decided:
  - The problem today. Every conductor works in the project's one checkout. Two started cards share its files, and one conductor switching branches changes the files under the other; the chat footer of every chat in the project shows the same branch. The brief never fetches and reads the epic page before it branches, so a conductor can work from a stale main (a conductor once reported its story missing from the epic page after it had been pushed).
  - What changes. Crew starts a new chat in its folder's project directory, the shared checkout, and only makes a worktree when a person presses "Start in new worktree" on a follow-up card, which apps may not call. The board does the same for every card by itself: it makes the worktree and opens the chat there. The board makes one Crew subfolder per started card, set to the worktree, and opens the chat in it. The Projects list leaves these subfolders out by their ids, because Crew does not mark them as the app's.
  - The person chooses, per project. The Projects view gets a setting on each project, "Start each story in its own worktree", on by default. The Start question says which will happen: "Works in its own worktree" or "Works in the shared checkout". With the setting off, the board works as it does today.
  - Fresh before reading. When a card starts, the board fetches origin, creates a worktree beside the checkout on the brief's branch (`story/<folder>`, or `story/<spec>-g<N>` for a task group) from origin's main, and opens the conductor's chat there, so the conductor and its workers read and work only in it.
  - Ready to build. The brief's first step runs the project's setup in the new worktree (for example `npm ci`), as its AGENTS.md says, before any check.
  - Catch up before the pull request. Before opening or updating the pull request, the conductor fetches, merges origin's main into its branch, resolves any conflicts, reruns the checks and says so in the chat.
  - Resuming and cleaning up. Reopening a card's chat reuses its worktree. A later task group starts a new worktree from the fresh main. When the person presses Finish session, the board removes the worktree, only when nothing is uncommitted or unpushed; otherwise the card says it was kept. There is no automatic cleanup.
  - Failure is visible. If the fetch or the worktree fails, the card says why and no conductor starts. It never falls back to the shared checkout.
  - Not in this story: merging, auto-merge, or resolving conflicts for the person. Shared resources such as ports and test databases stay with the project's own rules.
  - Open question, checked in Crew 0.12.2's source: Crew's worktree endpoint (`POST /api/worktree/create`) is for dashboard users only and refuses apps, so the board's backend runs git itself, as it already does for the plan. Chat creation for an app takes only a folder, so the board makes a subfolder of the project's folder per card (apps may create folders), which "Not in this epic" allows.
- [Briefs that hold up on any agent](../../.kiro/specs/briefs-that-hold-up-on-any-agent/) — done. Whatever harness and model a conductor runs on (Kiro, Claude Code, others Crew offers), it gets the same project instructions, checks its own work against the code, and leaves a record of what ran. Decided:
  - The problem today. Crew's harnesses load different instructions. When a project has its own `.claude/settings.local.json`, Crew runs the Claude Code harness with only the machine's user settings, so the project's CLAUDE.md, and the AGENTS.md it points to, never load; the brief's one line, "Read the project's AGENTS.md and steering files", is all it has. In a live case, a conductor on Claude Sonnet 4.6 wrote a design naming a database schema, a session setting and a table that don't exist. All three would have been caught by reading the code, and fixing them took two review rounds.
  - Instructions in the brief, not only a pointer. The board puts the project's own rules for agents into the conductor's first message, from AGENTS.md or another file the project names: or, if they're long, their headings plus "read these files before anything else", and the conductor confirms in the chat which ones it read. Every harness then starts from the same rules.
  - Check every name. A new step for spec work and for building: before opening the pull request, list every table, column, function, file, setting, endpoint and command the change adds or relies on. Mark each as existing (with the file where it was found) or new (with the task that creates it). Anything neither found nor created gets fixed before the PR. The list goes in the PR description.
  - Honest checks. The conductor reports the exact commands it ran and their results, including how many tests ran and how many were skipped. It never claims checks it didn't run.
  - Record what ran. The card and the PR description show the harness and model each conductor used (for example "Claude Code, claude-sonnet-4-6 on Bedrock" or "Kiro Agent, auto"). That lets the project compare harnesses and models on real work. The board reads these from Crew where Crew exposes them, and otherwise shows them as unknown. The brief also asks every conductor to end each commit message with a `Built-with: Kiro Crew, Epic Board (story: <story name>)` trailer, and each PR description with a footer line, "Built with Kiro Crew, started from Epic Board · Story: <story name> · <harness>, <model>", so every pull request shows how it was made, whatever the harness adds of its own.
  - Projects keep control. A project can add its own required checks, and the board includes them. The board adds no project-specific rules of its own.
  - Not in this story: choosing the model or harness for a card (Crew's settings decide that), and reviewing PRs on the person's behalf.
- Run a whole story — done. Built as a change to the briefs only, with no spec. A build conductor builds every task group of a story still to do on one branch, in order. After each group, a crew worker with a fresh context reviews it: it gets the spec folder, the branch and the group number, not the builder's summary, reads the diff against the spec and the code, and reruns the checks; a different model is used when Crew offers one. The conductor fixes what it finds and starts the next group only when the reviewer reports nothing left to fix. It stops only when a task needs the person, the spec leaves a question open, it and the reviewer disagree on the same finding twice, or a model or rate limit stops it, and then opens the pull request with what is built so far. One pull request per story lists each group, the reviewer's findings and their fixes, and the checks with their counts. Spec briefs now ask for tasks shaped for this: each group ends with the checks passing and names its tests, and steps that need the person sit in their own group at the end. The person still approves the spec and reviews and merges the pull request; the reviewer's pass is advice, not an approval. Not done: a Start choice between the next group and the whole story, and running several stories or a whole epic in one go.
